# Design

## Context

See proposal.md for motivation. What the codebase already provides (checked with `graphify query` and by reading the files):

- **Iframe apps already exist.** `IFrameApplication` (`src/system/iframe-application.js`) is only a thin base class that adds `_setupIframeForInactivity(iframe)`: it attaches `mousemove`/`mousedown`/`keydown` listeners to the iframe document so `window.System.resetInactivityTimer()` fires, and logs a warning instead of failing when the frame is cross-origin. `buy-me-a-coffee` (external URL) and `pinball` (local page) are the two reference implementations: create a `$Window`, build an `<iframe>` with 100% size and no border, inject it with `win.$content.html(iframe.outerHTML)`, then re-query the live element and call `_setupIframeForInactivity`.
- **Apps are not discovered at runtime.** `src/config/app-registry.js` is generated by `scripts/generate_registry.js`, which regex-extracts `static config = ...;` up to the first semicolon. The config must be a plain object literal with no semicolons and no logic. The registry is committed.
- **Desktop icons come from ZenFS, not from config.** `src/system/zenfs-init.js` writes `/C:/WINDOWS/Desktop/<name>.lnk.json` files (`{ type: "shortcut", appId }`) from a `defaultShortcuts` array, each only if the file does not exist yet. That check runs on every boot, which is why returning users also receive new defaults, and why a deleted default icon returns.
- **Start menu entries are automatic.** `start-menu-utils.js` creates a shortcut under `/C:/WINDOWS/Start Menu/Programs/<category>/` for every app whose `category` is defined; an empty string means Programs root (as for `buy-me-a-coffee` and `internet-explorer`).
- **Keyboard launch already works.** `desktop.js` launches the selected icons on Enter.
- **Icons**: `ICONS` entries are `{16, 32}` URLs built with `new URL(..., import.meta.url).href`. A precedent for an `.ico` used for both sizes exists (`simcity2000`).
- **The MSN side** (read-only inspection of MSN-working-clone): no `X-Frame-Options`, CSP or `frame-ancestors` is sent by its nginx, Express server or `index.html`, so it can be framed. It never reads `window.top`, `window.parent` or `frameElement`, and never calls `window.open`. Sign-in uses MSAL `loginPopup` with `redirect.html` and a same-origin `BroadcastChannel` bridge; the Discord redirect flow exists in code but is not used by the login page. The session lives in `localStorage` (`messenger_token`, `messenger_user`). MSN has no service worker, and the Win98 service worker is scoped to `/win98-web/`, so neither controls the other's pages.
- **Config rules**: `zenfs-init.js` is on the high-risk list, so the change to it must stay a single array entry. Tests are Playwright specs under `e2e/` that run the real app.

## Goals / Non-Goals

**Goals:**
- A launchable "MSN Messenger" app that frames the live MSN app with the least new code, following the `pinball` and `buy-me-a-coffee` pattern.
- Same behavior in the Docker deployment (same origin, URL `/`) and in local development (different origin, URL from env).

**Non-Goals:**
- Anything on the MSN side, session bridging, notifications, and the GitHub Pages build (see proposal Non-goals).

## Decisions

**1. New app `msn-messenger` extending `IFrameApplication`, no new shared code.** One file, about 40 lines, modeled on `buy-me-a-coffee-app.js` (an external-URL iframe with a single-purpose window).
- Alternative: reuse the Internet Explorer app and navigate it to MSN. Rejected: IE adds browser chrome and an address bar, which defeats the "MSN is installed in the OS" illusion, and its proxying and history behavior are unrelated.
- Alternative: a generic "web shortcut" feature. Rejected as over-built for one app.

**2. Config literal** (plain object, no semicolons, as the registry generator requires):
`id: "msn-messenger"`, `title: "MSN Messenger"`, `description: "Chat with your contacts."`, `icon: ICONS["msn-messenger"]`, `category: ""` (Programs root, period-accurate), `width: 380`, `height: 620`, `resizable: true`, `isSingleton: true`. The window is deliberately compact and portrait, like the original Messenger contact list, and well under the desktop size; the user can resize or maximize it (maximize stays at the default, true). MSN's own home screen is a full-height contact list (`h-screen`), and its login layout is fluid (`calc(100% - 2rem)` with max widths), so a narrow window is within what the MSN UI already handles. The final width and height are tuned against the real MSN UI in task 6.2, keeping the window narrower than half of a default-size desktop.

**3. URL resolution inside the app**: `const MSN_URL = import.meta.env.VITE_MSN_URL || "/";`. Vite only exposes `VITE_`-prefixed variables to client code, and it is replaced at build time, so the Docker image needs no new build argument for the default case (production is same-origin at `/`).
- Why `/` and not a path: in production MSN is the root of the domain and win98-web is under `/win98-web/` (see `serve-win98-under-path`). A relative `/` also avoids hardcoding the company domain.
- Development: `VITE_MSN_URL=http://localhost:5179 bun run dev` while MSN runs with `npm run dev:local` (frontend on 5179, backend on 3309). Documented in the app README. A `.env.example` line is added only if the repo keeps such a file (it does not today, so the README documents it instead).
- The default `/` is not valid under `bun run dev` alone (it resolves to the Vite root). The e2e spec therefore intercepts the frame request (decision 6), not the app.

**4. Iframe attributes**: `title="MSN Messenger"` (accessibility), `allow="autoplay; fullscreen; clipboard-write"` (MSN plays notification sounds and embeds a YouTube/Webamp player), width/height 100%, no border. Explicitly **no `sandbox`** attribute: `sandbox` would block MSAL's `window.open` popup, `localStorage` and audio. This is acceptable because the content is first-party and same-origin in production.
- Note on trust: a same-origin frame has full two-way access to the Win98 page and its storage. This is the same exposure already accepted in `serve-win98-under-path`; no new surface is created by the frame itself.

**5. Default shortcut via one `defaultShortcuts` entry** in `zenfs-init.js`: `{ name: "MSN Messenger.lnk.json", appId: "msn-messenger" }`. No migration code is needed because the existing loop already creates missing shortcuts for returning users. Start menu: no code, the `category` does it.
- Alternative: let users find it only in Start menu. Rejected: the request is a direct desktop access.

**6. Tests are Playwright e2e, written first.** `e2e/msn_messenger.spec.js` boots the real app (as `webamp_launch.spec.js` does), then:
- registers `page.route(url => url.pathname === "/", ...)` to answer the frame request with a tiny HTML page (`<title>msn-stub</title>`). That keeps the test independent of a running MSN while exercising the real window, registry and ZenFS paths (no mocking of ZenFS or `window.System`, per project rules);
- asserts the desktop icon, launch by double click, window title, frame `src`, singleton behavior (second launch focuses the same window, one `.window[data-app-id="msn-messenger"]`), and close removing the window and taskbar button.
- Keyboard launch and Start menu launch are covered in the same spec.
- The custom-URL scenario cannot be tested with a build-time variable inside the shared dev server, so it is verified manually (task 6.3) and by reading the config line.
- The returning-user scenario is tested by pre-seeding ZenFS through `window.fs` with a desktop that lacks the shortcut, reloading, and asserting the icon appears.

**7. Registry drift is not committed.** `bun run build:registry` currently also rewrites an unrelated entry (`report-a-bug` loses a stale `category: "Accessories"`, because its app source no longer defines it). That removes a Start menu category for an unrelated app, so the task keeps only the new `msn-messenger` block in the committed registry and leaves the other hunk out. The drift is reported to the user instead of fixed here.

**8. Docs**: app README with the required `## Screenshot` section and `screenshot.png`, a row in `src/apps/README.md` (Community & Support table, next to the other non-game, non-tool entries), and a short note of the `VITE_MSN_URL` variable.

## Risks / Trade-offs

- **[Risk] A compact 380x620 window may feel cramped for MSN's login form and chat panels, which were laid out for a full browser tab.** → Mitigation: the compact size is a product choice (it mimics the real Messenger), the window is resizable and maximizable, task 6.2 tunes the default size against the real login page, contact list and an open chat, and no MSN change is in scope.
- **[Risk] Browsers may block the Microsoft sign-in popup opened from inside a frame, or Entra may not have the redirect URI registered for the deployment origin.** → Mitigation: popups opened on a user click from a same-origin frame are allowed; the redirect URI is the existing production origin, unchanged. Verified manually on the deployed host (task 6.4), because it cannot be tested against Microsoft locally.
- **[Risk] Other deployments of MSN may later add `X-Frame-Options: DENY` or `frame-ancestors 'none'`, which would silently break the frame.** → Mitigation: recorded as a follow-up for MSN (`frame-ancestors 'self'`); the manual check in task 6.4 re-verifies it at rollout.
- **[Risk] Closing the window destroys the frame, so MSN presence goes offline (WebSocket closes).** → Accepted; MSN has a reconnect grace period and the session survives in storage. Minimizing keeps the session alive.
- **[Risk] Same-origin logout coupling**: signing out in the window signs out a separate MSN tab through the `storage` event. → Accepted for the internal deployment.
- **[Risk] `zenfs-init.js` is a high-risk shared file.** → Mitigation: the change is one array entry; the existing e2e specs that boot the desktop (`desktop_component.spec.js`, `desktop_extension.spec.js`) are re-run as the regression check.
- **[Risk] The GitHub Pages build would show a broken frame (`/` is not MSN).** → Accepted; out of scope, listed in Non-goals.
- **[Trade-off] The icon reuses the MSN favicon** (confirmed by the user; no official asset is available) and the default size is a judgment call tuned in task 6.2.

## Open Questions

- Does `$Window` clamp a window larger than the current screen (for example at a 640x480 monitor setting)? To be observed in task 6.2; if it does not, the app config may cap its size, which does not change the specs.
